# NeuroGrid next release implementation and test handoff

This is the target specification. The historical baseline used the legacy CPU pipeline. The [Granite candidate evidence](granite-beta-results.md) tracks the replacement and the open release gates.

Read the [architecture and diagrams](../architecture.md), watch the [animated walkthrough](neurogrid-next-architecture.mp4), and use the [current installation guide](../packaging/INSTALL.md) to reproduce the baseline.

## 1. Reproduce the reported desktop issue first

Open the **installed** package on Windows and Linux. In the legacy code, QSettings restores site, threads, duty cycle, and sign-in autostart. Site, threads, and duty cycle are saved only after a valid Start, and the controls are disabled during compute. The key depends on the OS keyring. The user reports difficulty returning to the limits after opening the app. Record the package version and reproduce editing without starting compute, closing to tray versus quitting, and relaunching under the same OS account. Check whether the packaged app differs from current source. Opening the GUI and starting a machine service are separate actions.

The standalone CLI is a foreground process with command-line flags. The repo also has a boot-enabled Linux installer for a legacy four-role host. Target a supported **single-contributor system service on Windows and Linux** using the same durable settings model as the desktop app. Start with the [desktop source](../compute/neurogrid_node/desktop.py), [CLI source](../compute/neurogrid_node/client.py), [Windows packaging](../packaging/windows/Install-NeuroGrid.ps1), and [Linux host installer](../packaging/linux/install-neurogrid-host.sh).

## 2. Ship real 8B chat with automatic input and output limits

- **Model.** Enable `ibm-granite/granite-4.2-8b` as the default next-release chat model when compatible capacity is available. Pin the exact model and tokenizer revisions, artifact hashes, chat template, numerical format, runtime build, and decoding settings. Add a Granite adapter and replace the hard-coded SmolLM2 tensor widths, token validation, and context constants with versioned manifests. Compare full and sharded execution at the same format using fixed seeds or deterministic test decoding. Measure answer quality separately when selecting a quantized serving build.
- **TwIL-8B.** Use the same Granite adapter for the balanced TwIL research model after checking its exact manifest. Keep TwIL outside the paid catalog until its publisher grants commercial permission. [IBM model and serving modes](https://huggingface.co/ibm-granite/granite-4.2-8b) · [TwIL model](https://huggingface.co/webAI-Official/TwIL-8B) · [TwIL license](https://huggingface.co/webAI-Official/TwIL-8B/blob/main/LICENSE.md)
- **Request.** The browser sends the authenticated prompt, a request idempotency key, and the displayed quote identifier when required. Remove the token picker, the client-controlled `maxTokens`, and the error telling the user to choose a shorter token limit. Apply an early request byte bound and count actual input with the pinned tokenizer and template. Explain when the prompt is too long. If conversation history is supported, trim only older turns under an explicit policy and preserve the latest prompt. Reject or ignore client attempts to override server limits as specified by the versioned API.
- **Profiles.** Use a non-thinking Granite profile for eligible simple requests and a longer profile for tasks that need it. Initial staging ceilings are 256 formatted input tokens and 64 new tokens for Quick, and 4,096 tokens of total context with at most 512 new tokens for Standard. Benchmark those ceilings before rollout. Count special tokens and generated reasoning as compute. Lower the ceiling based on the prompt, available balance, remaining context, and measured capacity before quoting. If a useful reply can’t fit, explain the required hold or bounded wait. A more expensive continuation requires a new visible quote. Avoid silently falling back to another model.
- **Quote and settle.** Show the maximum in credits before dispatch, such as “Up to 2 credits.” Bind the quote to the account, prompt or conversation fingerprint, model, rate version, and expiry. On Send, atomically recheck the balance and hold the quoted amount. If the quote increases, show the new quote before accepting it. Equivalent pinned failover must honor the ceiling. Afterward show actual charge, credits returned, and a clear completion or failure reason.
- **Acceptance.** Submit **“What is the capital of France?”** through the real 8B worker route. It returns **Paris** and charges **exactly 2 credits** once. Also submit the literal **“What is the capital of Paris?”**. It should clarify that Paris is a city and, if France was intended, Paris is its capital. It also qualifies for the 2-credit Quick rate. These are real inference checks. A canned answer, fake worker, or silent fallback to SmolLM2 fails acceptance. Include a longer task beyond the current 24-token output cap and compare the 8B model with the legacy model on a fixed factual, summarization, and reasoning evaluation set before claiming better quality.

## 3. Make each credit cover more compute

Use integer subunits internally and display user-facing credits. The staging rate card charges a **flat 2 credits** for a successfully delivered Quick reply within the profile above. For Standard, benchmark this initial stepped schedule before accepting purchases.

```text
charge = 2
       + ceil(max(0, formatted_input_tokens - 256) / 256)
       + ceil(max(0, generated_token_steps - 64) / 32)
```

A Standard job with 300 formatted input tokens and 80 generated steps costs 4 credits at that rate. Quote using the server-selected maximum output. A Quick job stays at 2 credits through retries. **100 credits cover 50 completed Quick requests** if that is all the customer runs. Measure worker compensation, network, verification, and operating costs before selling at that rate. Explicitly fund any pilot subsidy. Stream only accepted batches as provisional. Mark a partial failure clearly and refund the full hold for a failed or empty job under the first-release policy.

1. **Issue on confirmed purchase.** Replace the fixed 100,000-credit supply with paid issuance. Verify the signed Checkout event, paid state, currency, expected amount and quantity, and unique order/session identity. Atomically issue credits once per paid order, including delayed or duplicate events. The browser success page reports status.
2. **Reserve automatically.** Check spendable balance and move the maximum charge into a job hold in one transaction. A request retry returns the existing job. Any settlement must use the locked rate version and remain within the hold.
3. **Settle once.** Release unused hold, transfer the contributor share for accepted work, and retire the platform share. Split rewards by benchmark-weighted work, bound total reward by the charge, and pay once per accepted unit. The operator keeps fiat proceeds subject to outstanding compute obligations, reversals, and costs. If every spent credit must be retired, compensate contributors from cash revenue instead. A retired credit is removed from spendable supply.
4. **Example.** A customer buys 100 credits. A completed Quick job costs 2. At an illustrative split, transfer 1.4 to contributors and retire 0.6. The customer has 98, contributors have 1.4, and 99.4 remain outstanding. A failed job releases the entire hold exactly once.
5. **Migrate.** Preserve existing account balances with versioned ledger events or a deterministic new epoch linked to the last verified legacy head. Freeze legacy settlement at cutover, resolve pending jobs and Checkout orders, and state explicitly how legacy treasury inventory and outstanding sponsor allocations are handled. Replay opening balances plus issuance minus retirement and reversals. Keep holds, balances, and ledger events in one atomic authority. Reconcile refunds and chargebacks idempotently, including when the credits have been spent, without silently rewriting history. [Stripe Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment)

## 5. Start workers at computer boot

- **Windows.** Install a signed Service Control Manager-compatible host with automatic startup, a restricted service identity, and restart-on-failure recovery. A batch launcher alone cannot register as an SCM service process. Keep the configuration and model cache in service-owned application data. Provide status and logs, controlled shutdown, updates that preserve settings, and uninstall. [Microsoft service startup](https://learn.microsoft.com/en-us/windows/win32/services/service-startup)
- **Linux.** Provide a systemd system unit for one contributor profile with its own service account, boot enablement, restart on failure, protected credentials, and persistent model cache. A user unit or desktop autostart can serve login-only users. Give users systemctl and journalctl diagnostics and test install, upgrade, disable, and uninstall. [systemd service documentation](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)
- **Both.** Start before sign-in and connect as soon as networking, healthy credentials, and cached model data are ready. Use bounded backoff and jitter during network failures. Keep connection health, model readiness, owner pause, and bad credentials distinct. Restart after crashes with the same profile and identity. On intentional stop, drain or release work and clear transient state. As a staging target, reconnect a warm-cache worker within 60 seconds after networking is usable. Measure that on each OS, along with cold starts and extended outages.

## 6. Choose workers near the stateless request ingress

Define the “current stateless worker” as the Cloudflare/DeepSpace edge ingress admitting the chat request. Capture trusted metadata such as `request.cf.colo` when available and propagate it internally. It identifies the ingress data center and serves as a regional hint. Execution placement and Durable Object location can differ. Ignore caller-provided location headers. [Cloudflare Request metadata](https://developers.cloudflare.com/workers/runtime-apis/request/)

1. Track fresh, attested workers, warm contiguous block ranges, available memory, queue size, prefill and decode speed, failure rate, and measured network links. A self-reported capacity claim alone earns neither priority nor credits.
2. Measure from supported regional ingress or relay paths and between eligible workers. For a node behind NAT, measure the real relay path. Expire stale samples and use an explicit fallback for missing data. The legacy worker-to-coordinator ping measures a different link.
3. Filter for model/build compatibility, trust, contiguous coverage, readiness, and memory. Then score **complete routes** using ingress-to-first, all inter-worker hops, return path, queueing, and compute. Select the route with the best predicted first-token and decode latency within capacity and reliability constraints. Prefer a single worker with the full model when it wins. A nearby busy GPU can lose to a farther but faster healthy route.
4. Cache the KV state on assigned workers, pin healthy routes, and use short-lived leases, backpressure, and bounded queues. On failure, move to a verified checkpoint with a new lease epoch. Use direct encrypted worker streams where feasible and authenticated regional relays as needed. Keep tensor transfer off the credit transaction path and use DeepSpace RecordRoom for product status updates.

Let contributors add contiguous 10-layer blocks within their limits based on measured demand. Use real eligible work to compute rewards, weighted by benchmarked block cost and paid under a fixed job reward pool. Hosting an idle block or resubmitting a result does not create a reward. Offer more capacity on hot stages, co-locate adjacent blocks when it improves the route, and use added nodes to increase concurrency.

## 7. Verify receipts without full inference replay

- **First release.** Admit workers that prove an approved runtime is running in an allowed confidential environment. Verify CPU and confidential GPU evidence when applicable, along with issuer trust, reference policy, freshness, expiry, revocation, and binding to an ephemeral signing key inside the runtime. The runtime validates the pinned model manifest before accepting a scoped lease. Keep unattested hardware outside the attested paid lane.
- **Handoff.** Sign receipts for the job, model, runtime, layer range, lease epoch, window position, input and output commitments, KV-cache transition commitments, and metered units. The next stage checks the previous receipt and its incoming payload binding before computing. Use encrypted/authenticated transfers and request-specific hiding commitments for private values. The final receipt binds the decoded reply and usage. Keep prompts, raw activations, and replies out of the public ledger.
- **Anyone can verify.** Publish an open verifier and receipt schema. Independent verifiers can check signatures, attestation evidence and public policy, manifest, freshness at the relevant time, complete chain, and inclusion without a GPU, account, or prompt. The requester can open their own output commitment to check the returned result. Cache valid hardware evidence within its lifetime. On invalid evidence, retry an eligible worker or fail and refund. The legacy Python reference becomes an offline regression tool and is excluded from the accepted request path.
- **Proof milestone.** Prototype publicly verifiable mathematical validity proofs on a small deterministic model. Bind model weights, arithmetic, input/output, layer coverage, activation and cache continuity, and token selection. The public verifier checks the proof, and the prover pays its measured overhead. Benchmark before claiming useful interactive 8B proof latency. Hardware-backed receipts attest to a trusted execution environment. Mathematical proofs establish a statement about the specified computation. Expose which mode executed in the receipt and UI. [Remote attestation architecture](https://www.rfc-editor.org/rfc/rfc9334) · [NVIDIA confidential compute](https://docs.nvidia.com/confidential-computing/containers/dev/attestation) · [zkLLM](https://arxiv.org/abs/2404.16109)

## Animated walkthrough transcript

1. The user sends a prompt. The app sets input and output limits automatically and shows the maximum cost.
2. The edge ingress provides a regional hint. The scheduler ranks complete paths using measured delays and warm capacity.
3. Workers run consecutive Granite layers. A worker with more available memory can host more blocks and earn for accepted computation.
4. Each handoff carries a signed receipt. Independent verifiers check the evidence and chain without replaying inference.
5. The desktop and headless tools retrieve the same saved settings. Enrolled Windows and Linux services start at boot.
6. Paid purchases issue credits. The app holds the maximum automatically, releases unused credit, rewards workers, and retires the platform share.
7. Release requires real distributed inference, the two-credit Paris reply, public verification, and no-login reboots on Windows and Linux.
